# Sirius — отчёт по усилению безопасности

Дата: 2026-10-19

## Что изменено

1. **Убрано неявное создание аккаунта при аутентификации.** Раньше первый запрос с неизвестным ID мог закрепить за ним произвольный токен. Теперь обычные API и поток событий не создают аккаунты.
2. **Регистрация стала отдельной операцией.** Сервер сам назначает ID, проверяет уникальность username и лимитирует регистрации по IP. Профиль, токен и зашифрованный контейнер ключей создаются вместе.
3. **Добавлен отзыв сессии при выходе.** Сервер меняет токен и закрывает открытые потоки. Вход/восстановление с нового устройства также меняет токен.
4. **Основной токен удалён из URL EventSource.** Для потока используется одноразовый случайный билет сроком 45 секунд; билет нельзя повторно использовать, а отзыв сессии удаляет билеты пользователя.
5. **Медиа закрыто от анонимного доступа.** Чтение требует действующую сессию и совпадение владельца файла; ответы не кэшируются. Файлы новых загрузок доступны только владельцу.
6. **Ужесточены настройки хранения.** Каталог данных ограничивается правами `0700`, база/резервная копия/медиа — `0600` на POSIX-системах, где эти права поддерживаются.
7. **Усилены конфигурационные требования.** Новые пароли в интерфейсе — минимум 12 символов; `DEV_CODE` требует минимум 32 символа; `TRUST_PROXY` по умолчанию выключен; CORS не использует wildcard.
8. **Сохранены/усилены HTTP-защиты.** CSP с хэшем встроенного скрипта, `nosniff`, запрет встраивания, ограничение размеров запросов, отсутствие кэширования приватных API и дополнительные защитные заголовки.
9. **Добавлена очистка данных при удалении аккаунта.** При удалении пользователя сервер удаляет принадлежащие ему медиафайлы и записи владельца.
10. **Добавлены дополнительные HTTP-заголовки** `Cross-Origin-Resource-Policy: same-origin` и `X-Permitted-Cross-Domain-Policies: none`.
11. **Добавлены автоматические регрессионные проверки** через `npm test`.

## Что было проверено автоматически

`node --check server.js` — успешно.

Проверка встроенного JavaScript в `index.html` через `node --check` — успешно.

`npm test` проверяет:
- невозможность занять неизвестный ID обычным API-запросом;
- серверную выдачу ID и отказ при дублирующемся username;
- успешную авторизацию действительным токеном;
- одноразовый билет потока и отказ при повторном использовании;
- отзыв токена при выходе;
- запрет анонимного чтения медиа;
- удаление принадлежащего аккаунту медиа при удалении аккаунта.

## Чего этот отчёт НЕ утверждает

Это усиление кода и smoke-тесты, а не независимый аудит безопасности. Кнопки и все пользовательские сценарии не были полностью проверены в настоящем браузере. Не проверялись нагрузка, проникновение, утечки через логи хостинга, реальные звонки между устройствами и сценарии восстановления на продакшене. Поэтому честно присваивать проекту «9/10» пока нельзя.

## Обязательные шаги перед публикацией

- Развернуть только за HTTPS и проверить, что прокси не пишет токены/билеты и содержимое запросов в логи.
- Задать собственный случайный `DEV_CODE` минимум из 32 символов через защищённые переменные хостинга. Не записывать его в исходники/архивы. Секрет, опубликованный в переписке, заменить после тестирования.
- Оставить `TRUST_PROXY=0`, если не проверена схема прокси. Если есть прокси, задать число хопов в `TRUST_PROXY` и точный allowlist `TRUST_PROXY_IPS` (IP/CIDR непосредственных прокси); без allowlist forwarded-заголовки игнорируются.
- Не публиковать `.env`, `data/`, `db.json`, `db.json.bak` и TURN-секреты; ограничить доступ к резервным копиям.
- Настроить TURN с временными/ротируемыми учётными данными, если нужны звонки.
- На двух реальных аккаунтах проверить регистрацию, вход, смену/восстановление пароля, выход, удаление, блокировки, права на переписки, работу после перезапуска и звонки.


## Дополнительные изменения (2026-10-19)

- Добавлена загрузка локального `.env` без сторонних зависимостей; переменные, заданные хостингом, имеют приоритет. Файл `.env` исключён из Git. В продакшене предпочтительны секреты панели хостинга.
- TURN больше не использует постоянные TURN_USERNAME/TURN_CREDENTIAL. При наличии TURN_SHARED_SECRET сервер формирует временные учётные данные coturn REST API с ограниченным сроком действия, привязанные к ID пользователя. На TURN-сервере должен быть настроен тот же `static-auth-secret`.
- Эти изменения не заменяют распределённые лимиты Redis, проверку авторизации для всех коллекций, миграцию сессионных ключей и внедрение проверенного протокола E2EE.


## Дополнительный этап (19.10.2026)

- Добавлен необязательный распределённый rate limiter на Redis для POST API с атомарным INCR+EXPIRE через Lua. При заданном `REDIS_URL` и недоступном Redis API-запросы закрываются с 503; без `REDIS_URL` действует только локальная защита процесса.
- Расширены автоматические тесты: получатель не может изменить тело чужого сообщения, подделать сообщение отправителя, а третий аккаунт не должен получить личную переписку в начальном состоянии.
- `npm test`, `node --check server.js` и `node --check security-smoke-test.js` прошли.
- Полноценный Double Ratchet не внедрён: текущий клиент использует долгоживущие ECDH-ключи и повторно используемый ключ на собеседника. Подробности и безопасный план миграции — `CRYPTOGRAPHY-ROADMAP.md`. Не считать forward secrecy / post-compromise security реализованными.

## Усиление после повторного замечания владельца (19.10.2026)

- В production включён режим обязательного HTTPS по умолчанию; его можно явно включить через `REQUIRE_HTTPS=1`. HTTP-запросы без TLS отклоняются кодом 426.
- До v15 `X-Forwarded-Proto` учитывался при `TRUST_PROXY > 0`; начиная с v15 дополнительно проверяется непосредственный адрес прокси по `TRUST_PROXY_IPS`, а цепочка forwarded-протоколов должна соответствовать настроенному числу хопов.
- JSON API отклоняет POST-запросы без `Content-Type: application/json`.
- Повторно пройдены `node --check server.js` и `node security-smoke-test.js`.

Это реальные дополнительные проверки транспорта и формата запросов, но не реализация Double Ratchet. Текущий клиент всё ещё не имеет полноценного протокола уровня Signal: долгоживущие ECDH-ключи, отсутствие проверенной схемы signed/one-time prekeys и полноценной forward secrecy остаются существенными ограничениями. Нельзя заявлять равенство Telegram/Signal до миграции на проверенную библиотеку, тестирования и независимого криптографического аудита.


## Дополнительное усиление клиента и ключей (19.10.2026)

- Новые личные сообщения используют E2E envelope v2: свежая случайная соль HKDF на каждое сообщение, AES-256-GCM и AAD, связывающий шифротекст с идентификаторами беседы, отправителя, получателя, сообщения и временной меткой. Старый формат v1 остаётся только для чтения старых сообщений.
- Добавлен тест, который извлекает реальные функции E2E v2 из `index.html` и проверяет обмен между двумя ключами WebCrypto, уникальность конвертов, обнаружение подмены ID/получателя и изменения шифротекста.
- Приватный JWK и токен сессии больше не записываются в `localStorage`; при загрузке очищаются значения, оставшиеся от прежней версии. После перезагрузки нужен повторный вход.
- Публичные ключи проверяются сервером как валидные EC P-256 JWK. Добавлено локальное закрепление ключа собеседника, предупреждение/блокировка отправки при изменении и явное действие для подтверждения ключа после внешней сверки кода.
- Автотесты дополнены проверками неверного ключа и обязательного JSON Content-Type. `node --check server.js`, проверка синтаксиса встроенного клиентского JavaScript и `npm test` проходят.

Эти меры повышают целостность сообщений и уменьшают риск кражи долговременных секретов из сохранённого браузерного хранилища. Они не заменяют Double Ratchet, не обеспечивают forward secrecy, не устраняют риск активного XSS и не подтверждают безопасность первого контакта без внешней сверки ключей. Независимый аудит не проводился.

## Сохранение входа между запусками (19.10.2026)
- Добавлено автоматическое восстановление действующей сессии через IndexedDB после перезагрузки страницы.
- Токен сессии и экспортируемое представление приватного ключа хранятся только внутри AES-GCM-зашифрованного пакета в IndexedDB; ключ шифрования AES сохраняется как non-extractable CryptoKey. Секреты не помещаются в localStorage.
- При восстановлении клиент проверяет сессию на сервере до запуска интерфейса; недействительная/повреждённая сессия удаляется.
- Ручной выход очищает локальную сессию и отзывает серверный токен через существующий endpoint.
- Ограничение: это защита данных при обычном чтении хранилища, но не от XSS или скомпрометированного same-origin JavaScript, который может использовать ключ/сессию в браузере. Для защиты от такого класса атак нужны HttpOnly Secure SameSite cookies и серверные сессии.

## Усиление проверки ключей (19.10.2026, v5)
- Первое сообщение контакту теперь не отправляется, пока пользователь явно не откроет код безопасности и не закрепит проверенный ключ.
- Входящие E2E-сообщения не расшифровываются, если ключ отправителя ещё не проверен либо отличается от закреплённого.
- Смена ключа остаётся блокирующим событием; пользователь должен сверить код по независимому каналу перед закреплением нового ключа.
- Добавлен регрессионный тест, который проверяет fail-closed поведение на отправке и получении.
- `npm test` проходит, включая проверку E2E round-trip, подмены шифротекста/метаданных, авторизации и нового режима проверки ключей.

Ограничения остаются: ECDH использует долгоживущие ключи; нет проверенного Double Ratchet, полноценной прямой секретности и post-compromise security; локальное закрепление не заменяет независимую проверку отпечатка и не защищает от активного XSS/компрометации устройства. Поэтому данное изменение улучшает защиту от подмены ключа, но не доказывает равенство Telegram Secret Chats.

## Дополнительное усиление v6 (19.10.2026)
- Для изменяющих состояние браузерных POST-запросов проверяется `Origin`: разрешены собственный origin и точные значения из `ALLOW_ORIGIN`; чужой origin отклоняется. Запросы без `Origin` по-прежнему требуют действующий токен и предназначены для не-браузерных клиентов.
- Добавлен базовый in-memory лимит до 600 POST-запросов в минуту на IP даже без Redis. Redis остаётся необходимым для единого лимита между несколькими процессами; этот лимит не заменяет защиту на reverse proxy/WAF.
- Сервер проверяет сигнатуру байтов PNG/JPEG/WebP/GIF, а не доверяет только заявленному MIME в data URL. Это проверка сигнатуры, не полноценная декодирующая/антивирусная проверка изображения.
- Неожиданные ошибки сервера логируются на серверной стороне и возвращают клиенту общее сообщение; ошибки разбора JSON остаются ошибками запроса.
- Production-режим отклоняет очевидные шаблонные значения `DEV_CODE`; пример `.env` больше не содержит длинный комментарий, который мог ошибочно интерпретироваться как значение секрета.
- Регрессионные тесты проверяют блокировку чужого `Origin`, работу same-origin, отказ от поддельного PNG, приём валидного PNG, авторизацию, целостность сообщений и закрепление ключей.

Это усиливает HTTP-границу, загрузки и базовую устойчивость к злоупотреблениям, но **не делает криптографию эквивалентной Signal/Telegram Secret Chats**. Не реализованы проверенный Double Ratchet, полноценная forward secrecy/post-compromise security и независимый аудит. Итоговую оценку 7/10 пока нельзя честно заявить.

## Дополнительное усиление v7 (19.10.2026)
- Восстановление аккаунта больше не возвращает фиктивный UID в заметно отличающемся формате: для неизвестного имени выдаются восьмизначный фиктивный UID и соль того же формата. Это уменьшает возможность перечислять существующие аккаунты по одному только ответу `rec/start`; полностью скрыть все побочные каналы без отдельного аудита нельзя.
- При смене облачного пароля сервер ротирует случайный токен сессии и закрывает старые потоковые подключения/билеты. Клиент сохраняет новый токен и переподключается автоматически; украденный прежний токен перестаёт работать.
- Удаление аккаунта теперь требует повторного подтверждения облачным паролем. Одного украденного токена сессии недостаточно; неверное подтверждение блокируется, попытки ограничиваются, а принадлежащие аккаунту медиа удаляются только после успешного подтверждения.
- Добавлены регрессионные проверки формата ответов восстановления, отзыва старого токена при смене пароля, работы нового токена и отказа в удалении аккаунта при неверном подтверждении. `npm test` и проверка синтаксиса встроенного клиентского JavaScript проходят.
- Эти изменения усиливают защиту аккаунта и восстановление доступа, но не заменяют 2FA/passkeys, полноценное управление устройствами, независимый аудит и миграцию E2E на проверенный протокол.

## Дополнение v8 — срок жизни сессий

Срок сессии скользящий: при активности он продлевается, а после года полного бездействия токен отзывается. Выход, смена облачного пароля и восстановление отзывают прежний токен; проверка действует и после перезапуска сервера. Это не заменяет MFA, управление отдельными устройствами или независимый аудит.

## v9 hardening addendum (2026-10-19)

- Authenticated sessions use a rolling expiry: activity extends the session, and 365 days without activity revoke the token. Activity is persisted at a bounded interval; expired sessions have their token hash rotated and their SSE streams closed.
- Media upload file IDs and per-user quota are reserved while asynchronous disk writes are pending. This prevents concurrent duplicate-ID uploads and quota check races. Upload completion revalidates that the account and session still exist; stale uploads are deleted rather than attached to an account.
- Added integration tests for idle session expiry after restart and concurrent duplicate media uploads.
- These changes reduce specific session-theft and storage-abuse risks; they do not establish an independent security rating or fix the known E2E forward-secrecy limitations.
- Media reads require a bearer token in the `Authorization` header instead of accepting the session token in the URL query. URL tokens can leak into access logs and diagnostics; the endpoint now only allows GET. Integration tests cover both rejection of query-string tokens and acceptance of the bearer header.

## Этап v12 (19.10.2026)

- Для изменения профиля введён allowlist полей: клиент больше не может отправлять произвольные серверные свойства, включая телефон/hidden и произвольные поля с ролью/правами. Проверяются типы и длины значений.
- Добавлена проверка целостности состава групп: уникальные существующие участники, администраторы только среди участников, владелец остаётся участником и администратором.
- При удалении аккаунта удаляются его группы и сообщения этих групп, связанные заказы, данные восстановления/сессии, медиа и аудит-записи, привязанные к ID пользователя.
- Некорректный request-target и неоднозначные заголовки длины запроса отклоняются. Общий POST rate limiter исправлен: теперь он использует отдельную ограниченную по размеру карту счётчиков, а не историю неудачных попыток, у которой ограничение событий было меньше порога POST-лимита.
- Регрессионные тесты проверяют перечисленные сценарии; `npm test` прошёл. Это повышает качество серверных проверок, но не заменяет внешний аудит и не устраняет ограничения текущего E2E-протокола.

## Дополнительное усиление v13 (19.10.2026)
- Поток SSE теперь ограничивает объём уже ожидающих отправки данных для одного клиента 4 МиБ; медленный клиент отключается вместо неограниченного накопления буфера Node.js.
- Реестр одноразовых билетов SSE имеет жёсткий предел 5 000 активных записей: сначала очищаются истёкшие билеты, затем новые выдачи временно отклоняются, если реестр всё ещё заполнен.
- Базовые browser-security headers выставляются до ранних выходов HTTP-обработчика, включая ошибки request-target, запрет Origin и обязательный HTTPS.
- Введены ограничения длины request-target, пути и query до обработки маршрутов.
- Аватары/обложки, переданные как data URL, проходят проверку сигнатуры PNG/JPEG/WebP/GIF; произвольные и неправильно помеченные данные отклоняются.
- Регрессионные тесты проверяют заголовки раннего ответа, длинный request-target, отклонение поддельного изображения и приём валидного PNG; все 16 групп проверок проходят.

Эти изменения уменьшают отдельные риски отказа в обслуживании и подделки типа изображения. Проверка сигнатуры не заменяет полноценное декодирование/сканирование файлов; ограничение SSE может отключать очень медленные соединения. Независимый аудит не проводился, а ограничения E2E-криптографии из предыдущих разделов остаются.


## Дополнение v15 (19.10.2026)

- **Политика личных сообщений проверяется сервером.** Создание новых DM теперь блокируется, если получатель включил `fonly` и отправитель не является другом, либо если между пользователями действует блокировка. Проверка в интерфейсе не считается границей безопасности.
- **Идентификатор личного диалога строгий.** Личные диалоги требуют ровно два существующих UID в каноническом порядке; многопользовательские поддельные ID не принимаются. ID новых групп не может совпадать с шаблоном личного диалога.
- **Строгая схема сообщения.** Неизвестные поля в записи сообщения отклоняются, чтобы клиент не мог протащить произвольные поля в общее состояние.
- **Доверие к reverse proxy ограничено адресами.** `X-Forwarded-Proto` и `X-Forwarded-For` учитываются только если TCP-пир попадает в `TRUST_PROXY_IPS` (IP/CIDR). Самого `TRUST_PROXY` недостаточно. Это закрывает возможность прямому клиенту подделать HTTPS и IP через forwarded-заголовки.
- Добавлены регрессионные проверки для обхода `fonly`, блокировок, multi-party ID, дополнительных полей сообщения и доверия к прокси. Полный `npm test` пройден.

**Оценка границ:** v15 улучшает реальные серверные проверки, но это не доказывает равенство безопасности VK. E2E остаётся самодельным протоколом без проверенного Double Ratchet / полной защиты после компрометации; независимого аудита не было. См. `RELEASE-NOTES-v15.md` и `SECURITY-RELEASE-CHECKLIST-v15.md`.

## Дополнительное усиление v16 / 1.9.0 (19.10.2026)
- Закрыт обход политики E2E: новые личные сообщения теперь принимаются только в формате `kind: e2e` с поддерживаемой версией конверта; флаг `e: 2` больше не позволяет отправить открытый текст как якобы зашифрованное сообщение.
- Исправлен общий трекер неудачных попыток: после фильтрации старых событий обновлённый массив теперь сохраняется обратно в таблицу ограничений. До исправления последующие события могли не накапливаться должным образом.
- Исправлена асимметричная проверка блокировок у подарков: запрет срабатывает, если заблокировал отправитель или получатель.
- Добавлены отдельные лимиты подарков (20 попыток/минуту на аккаунт) и создания заказов (10/минуту на аккаунт). Они процессные; для нескольких инстансов требуется общий limiter.
- Идентификаторы подарков и служебных сообщений используют криптографически случайные суффиксы вместо `Math.random()`.
- `npm test` проходит, включая новые регрессионные проверки на plaintext downgrade, блокировку подарка и лимит подарков.

Это устраняет найденные ошибки реализации, но не является независимым аудитом и не устраняет архитектурные ограничения протокола E2E.

## Дополнение v17 / 1.10.0 (19.10.2026)

- Исправлена выдача телефона: `fph` теперь означает «только подтверждённым друзьям», а не всем пользователям, получающим состояние профиля.
- Для невидимых профилей поле `seen` исключается из данных, отданных другим пользователям; владелец продолжает видеть собственный профиль.
- Добавлены серверные лимиты отправки новых сообщений: 40/мин на аккаунт и 15/мин на один допустимый диалог/группу. Лимитер не создаёт отдельные ключи для произвольных, невалидных ID.
- Сервер проверяет структуру E2E-конверта v2 и допустимый размер старого формата v1; случайная строка больше не принимается как корректный шифротекст. Это проверка формата, а не криптографическое подтверждение, что содержимое зашифровано под правильный ключ.
- Добавлен интеграционный тест на выдачу номера другу/постороннему и сокрытие last-seen. Общий `npm test` проходит.

Это реальные исправления приватности и ограничения спама. Они не являются подтверждением полной эквивалентности VK и не устраняют отдельно отмеченные ограничения E2E-протокола.
